# 幂等性设计：为什么重复请求不能出问题

用户点了"提交订单"按钮，网络慢，他又点了一次。或者消息队列重试了一次，同一个消息被消费了两遍。如果不做幂等性处理，结果就是：用户付了两次钱、订单创建了两次、积分加了两遍。幂等性是分布式系统中必须考虑的问题——同一个操作执行一次和执行多次，结果应该一样。

## 一、什么是幂等

幂等（Idempotent）是一个数学概念：f(f(x)) = f(x)。在编程中，一个幂等操作执行一次和执行多次的效果相同。

HTTP方法的语义天然有区分：GET是幂等的（查多少次都一样），POST不是幂等的（提交两次创建两条数据），PUT是幂等的（更新同一条记录，执行多次结果一样），DELETE是幂等的（删两次和删一次效果一样）。

但实际业务中，POST创建订单、POST支付这种操作，如果用户重复提交或者消息重复投递，就会出问题。

## 二、怎么实现幂等

最直接的方案：给每个请求一个唯一的请求ID。客户端生成一个唯一ID（UUID或者雪花ID），和请求一起发给服务端。服务端先查这个ID有没有处理过——处理过就直接返回上次的结果，不重复执行。

这个方案本质上是用一个唯一键做去重。数据库里建一张请求记录表，请求ID做唯一索引。处理前先插入记录，插入成功说明是第一次请求，执行业务；插入失败说明是重复请求，直接返回。

## 三、天然幂等的操作

有些操作天然幂等，不需要额外处理： - 查询操作：查多少次结果都一样。 - 更新固定值：update set status = 1 where id = 123。执行多少次结果都是status=1。 - 删除操作：delete from where id = 123。删一次和删十次，结果都是这条记录没了。

不幂等的操作： - 新增：insert into orders ...。执行两次创建两条订单。 - 累加：update set balance = balance + 100。执行两次加200，不对。

对于累加操作，改成set balance = balance + 100 where order_id = 'xxx' and processed = false——用条件控制，已经处理过的就不再累加。

## 四、消息队列的幂等

前面说过消息队列可能重复投递。消费端必须做到幂等——同一个消息消费两次，结果和消费一次一样。

最常见的做法：消息带一个唯一业务ID（比如订单号），消费前先查这个ID是不是已经处理过了。处理过就跳过。数据库唯一约束也能兜底——同一个订单号的积分记录唯一，重复插入会失败。

## 五、总结

幂等性不是可选项，而是分布式系统的必备设计。网络会超时、用户会重复点击、消息会重复投递——你无法保证操作只执行一次。但你可以保证执行多次结果和一次一样，这就是幂等性的价值。
