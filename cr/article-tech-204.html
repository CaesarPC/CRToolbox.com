# REST之外：GraphQL、gRPC与API设计的新选择

RESTful API统治了Web世界十几年，但它不是没有缺点。前端经常抱怨：一个页面要调三四个接口才能凑齐需要的数据；后端返回的字段太多，大部分用不上；要加一个字段还要后端改接口、发版，前端等着。这些痛点催生了新的API设计范式——GraphQL让前端精确声明需要什么数据，gRPC让服务间通信更快更高效。理解这些新范式的优缺点，知道什么场景该用什么，是现代后端开发者的必备知识。

## 一、REST的痛点：过度获取与不足获取

假设你在做一个用户列表页面，要显示每个用户的名字和最新一条动态。REST的做法是：先调 /api/users 拿到用户列表，然后对每个用户调一次 /api/users/{id}/posts 拿到最新动态。一页20个用户，就是21个请求——首屏加载慢得要命。

反过来的问题是过度获取：你只是要显示用户名字，接口却返回了用户的邮箱、手机号、地址、订单记录一大堆字段。数据传了一大堆，绝大部分没用。

这些问题的根源是：REST接口的形状是后端定义死的，前端只能被动接受。后端不知道前端需要什么，前端没法精确告诉后端。两边来回沟通改接口，效率很低。

## 二、GraphQL：前端说了算

GraphQL是Facebook开源的API查询语言。它的核心思想是：前端不指定"访问哪个URL拿什么数据"，而是写一个查询，精确声明自己需要哪些字段、嵌套关系是什么。后端只暴露一个端点（通常是 /graphql），所有请求都发到这里。

举个例子，前端要查用户的名字和最新动态的标题，就写这样的查询： query { user(id: 123) { name posts(limit: 1) { title } } } 后端根据这个查询，只返回 name 和 posts.title 这两个字段，不多不少。

GraphQL的好处是显而易见的。第一，按需取数：要什么字段拿什么字段，没有多余数据。第二，一个请求拿全嵌套数据：上面那个例子，一个查询同时拿到用户和他的动态，不用发多个请求。第三，前端迭代不用等后端改接口——要加字段就自己在查询里加上，后端schema里有的话直接就能用。

但GraphQL不是没有代价。学习成本比REST高——你要学schema定义、resolver、查询语法。缓存也更复杂：REST的URL天然就是缓存key，GraphQL所有请求都打到同一个URL，缓存策略要自己设计。N+1查询问题也需要特别处理——如果不做优化，GraphQL可能会生成一堆低效的数据库查询。

GraphQL特别适合前端需求多变的场景：内容平台、B端管理系统、移动端App。但简单的CRUD接口，REST就够了，没必要上GraphQL。

## 三、gRPC：高性能的服务间通信

REST用JSON做数据格式，走HTTP，可读性好但性能一般。gRPC是Google开源的高性能RPC框架，用Protocol Buffers做序列化，基于HTTP/2传输。

gRPC的工作方式是：你用.proto文件定义服务接口和数据结构，然后用工具自动生成各语言的客户端和服务端代码。调用远端方法就像调用本地函数一样简单——不用手动拼接URL、不用手动序列化JSON。

gRPC的性能优势主要来自Protocol Buffers。它是二进制格式，比JSON小得多、解析快得多。一个普通的JSON请求可能几百字节，Protobuf可能只有几十字节。在高并发服务间调用的场景下，这个差距累积起来非常可观。

gRPC适合什么场景？微服务之间的内部通信——服务A调用服务B，追求低延迟和高吞吐量。它不适合直接暴露给前端浏览器——浏览器不能直接发gRPC请求（需要gRPC-Web做转换），而且二进制格式对人不友好，调试不方便。

所以常见的架构是：对外暴露REST或GraphQL API给前端，内部服务之间用gRPC通信。各取所长。

## 四、API设计的本质：不是风格之争

REST、GraphQL、gRPC不是互相取代的关系，它们解决不同的问题。

REST简单、通用、调试方便，适合对外的公开API。GraphQL灵活、按需取数，适合前端需求多变的B端和C端产品。gRPC高性能、强类型，适合内部微服务通信。

很多人纠结"我们应该用REST还是GraphQL"，好像选了一个就要抛弃另一个。实际上，一个成熟的系统往往是混合的：核心对外接口用REST保持简单，复杂查询场景用GraphQL，内部服务间用gRPC。选技术的时候不要原教旨主义，根据场景选最合适的。

## 五、API的未来：从手写代码到自动生成

无论用哪种风格，API设计的趋势都是自动化。OpenAPI规范让你用一份描述文件定义API，自动生成文档、SDK、mock数据。GraphQL的schema自带文档和类型系统。gRPC的proto文件就是接口定义。

未来的开发者花在手写API样板代码上的时间会越来越少。AI可以根据你的业务描述自动生成接口定义和CRUD代码。但理解API设计的原则——一致性、可扩展性、安全性——这些不会因为工具自动化而过时。

## 六、总结

API设计是前后端协作的桥梁。这座桥设计得好，两边通行顺畅；设计得差，天天堵车。REST是基础，必须掌握；GraphQL和gRPC是进阶工具，知道什么时候用。不要被技术名词吓住，核心永远是：你的调用方需要什么，你怎么最高效地把数据给他们。
